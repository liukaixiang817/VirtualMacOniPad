# 2.0.0 beta3 and later: standalone release requirements

The user's 2026-10-21 requirements supersede the old beta1 packaging contract.
The user renewed publication authorization on 2026-10-22 and explicitly selected
the public liukaixiang817/VirtualMacOniPad repository after its visibility was
checked. Beta2 has been published there as a pre-release from commit158eba7,
with the frozen deb and six companion assets. The current diagnostic App is
not a beta3 release.

On 2026-10-21 the user manually accepted the current startup speed and reported
that the gray desktop no longer appears. This supersedes the earlier unmet
startup-experience statements below; those measurements remain historical
evidence, not a reason to keep optimizing login indefinitely. It does not claim
a newly measured 30-second cold Ready time. Finish the local cross-CPU GIC
invalidation and repeated exit-read overhead changes, check only for obvious
regression, then prioritize App launch and window dragging performance.

The next acceptance order is App launch/window motion, Magic Keyboard
multifinger guest gestures, audio, networking, shared clipboard and guest
pause/resume. Every visible VM setting must control its actual function. The
backend selector must offer exactly two choices: the complete macOS13 stack
or the complete macOS27 stack. No mixed third option is requested.

On 2026-10-22 the user also authorized deferring unsupported Bluetooth audio,
while requiring ordinary audio to remain independent. Runtime150/App211 now
disables only the owned VMM's rejected Bluetooth HAL endpoint; the actual busy
reconnect queue disappeared. Speaker device admission and native guest playback
completion passed, while physical acoustic output and microphone remain separate
acceptance items. See [audio isolation](independent27-audio-isolation.md).

The latest user priority defers icon work until the wallpaper/login regression
is fixed. The reference is the original complete 1.2.3 macOS13 stack, including
its GPU, rather than a hybrid CPU13/GPU27 configuration. Normal212 measured
6.533 seconds from actual password Return to native WallpaperImageExtension
acquire completion. Independent27 CPU77 measured 44.625, 46.828 and 45.831
seconds in Normal214–216. CPU78 measured 39.752 seconds in Normal217; CPU79
measured 42.908 seconds in Normal218 with a concurrent 3-second native profile.
These are service events, not proof of a visually complete or actionable
desktop. Both new runs still showed gray background at the 36-second capture.
High CPU load during login is a regression symptom, not accepted behavior.

CPU78 introduced GIC14 timer-local invalidation and Life70's private guarded
poll. CPU79 introduced Production15's finite ready-bank C1 transaction; its
native trace proved execution, but unready banks still spent substantial time
in the generic path. The following candidate was Runtime137 / CPU80 /
Production16 / Life72 / App199. It retains genuine native8 bank saves before
retrying the same concrete transaction and uses compiler-owned local arguments
inside the sole private Run-step caller. Public input/output checks, original
keys, dirty banks, native version reads, per-field readback and generic callback
behavior remain. This candidate has not yet passed the no-gray acceptance.

The highest priority is actual daily use: no prolonged gray desktop during
login, complete native Settings/Dock icons, responsive window dragging and
reliable Magic Keyboard pointer/keyboard operation across foreground changes,
touch use and UIKit layout changes. A late wallpaper or successful isolated
render is not complete Ready desktop. The cold-start target is approximately
30 seconds to the complete desktop and wallpaper; it remains unmet.

The final deb must include the tested App input/display fixes and Main50
SIGPIPE disconnection protection (see independent27-disconnect-crash.md), and
provision the validated guest compatibility policy automatically. Preferences manually set
only in the development guest are not a complete installation feature. A clean
guest and an upgraded guest both need actual startup/input/GUI validation.
Failed experiments, including the early wallpaper kickstart-only job tested in
Normal202, must not be enabled by the package.

The 2.0.0 package must operate without Virtual Mac 1.2.3. It must not depend on
`com.mac.virtual`, import its private files or rely on helpers under its runtime
root. Include and own the installation, networking, Guest Tools and runtime
components actually required by either backend. Preserve user VM bundles and
settings during upgrade and removal.

Offer actual macOS 13.2.1 and independent macOS 27 CPU/VMM/Virtualization
backends in Settings, with separate owned runtime roots. Persist the choice,
pin it for a running VM, refuse changes during startup/installation/run and
require an App restart before loading a different framework graph. Failure of
one backend must not silently run the other. Both choices require actual guest
execution tests from the installed deb after the old package is absent.

The old `packaging/virtualmac2/DEBIAN/control` still depends on 1.2.3, and the
current diagnostic independent27 selector accepts only 27. Neither qualifies as
the requested final dual-backend package. The beta2 packaging snapshot is also
not the final beta3 product. Do not publish those artifacts with these claims.
