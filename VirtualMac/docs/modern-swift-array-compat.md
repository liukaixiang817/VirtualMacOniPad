# Scoped Swift array compatibility for DIKit 27

This work supplies eight `AnyObject` Array/ContiguousArray specialization
functions and a separate, genuine Swift subclass metadata factory. It does not
provide a complete Swift 27 runtime or a runnable Virtualization 27 stack.

## Eight typed array functions

`vz/host/modern_swift_anyobject_array_compat.swift` implements the eight exact
Swift specialization symbols imported by DIKit 27. The functions preserve the
compiler's Swift calling convention, instance `self`, owned element arguments,
and owned return values. Their bodies use the standard library's serialized
array operations. `_endMutation` uses the real `Builtin.endCOWMutation`; its
optimized `ret` is generated by Swift rather than a handwritten stub.

The build targets macOS 13.0/iOS 16.1 so the compiler materializes those bodies.
Targeting macOS 27 instead selected the same exported specialization recursively;
that failed oracle is retained in the diagnostics. The builder changes only the
visibility of the otherwise hidden `_ArrayBuffer` getter. It does not alter its
function body or ownership ABI.

The frozen candidate is
`DeviceDiagnostics/2026-10-08-full-macos27-cpu-vmm/swift-anyobject-array-build-v5`.
The private provider UUID is `9eb1cd0591193a9dba1eb7a0ce9869ee`. The executable
checks all eight loaded entry addresses against that UUID and its exact sibling
provider path before invoking them. It covers empty and shared storage, growth,
copy-on-write, element ownership, and final object destruction.

The actual iPad receipt is `swift-anyobject-array-native-v1/result.json`: direct
child PID 34088 exited 0 and was absent afterwards, with 5,120 checks, no failures,
and 4,608 object destructions. All eight entry identities matched the private
provider. It performed no VM or disk operations. The NSArray round-trip case is
behavioral coverage; the receipt does not establish that iPad storage used the
Cocoa branch. An additional Mac-only oracle checked actual non-native Cocoa
storage and passed 5,632 checks. Invalid-index controls trapped on the Mac.

## Real completed subclass metadata

`vz/host/modern_swift_static_array_metadata_compat.swift` defines a real Swift
subclass of the host runtime's `__ContiguousArrayStorageBase`. Its two private
bridge override records use the verified parent method descriptors at offsets
60 and 68. `swift_getSingletonMetadata` and `swift_initClassMetadata2` allocate
and complete the subclass and sign its virtual table. The implementation does
not copy metadata from another class or alias an old class to the missing CN.

The frozen metadata candidate is `static-array-metadata-build-v8`. The actual
iPad receipt is `static-array-metadata-native-v1/result.json`: direct child PID
34229 exited 0 and was absent, with 130 checks and 101 factory calls. The loaded
provider UUID was `2daf0f4f47f735db882bac8329d9b796`, using the real iPad Swift
Core UUID `f896d145e02539d6afd3bc0a2ad4f839`. The completed class had a real Base
superclass, a 32-byte instance, alignment mask 7, and the old runtime's 16-byte
class address point.

That receipt validates metadata initialization only: it made no virtual calls,
constructed no static array objects, and loaded no DIKit. The candidate exports
no `__StaticArrayStorageCN`; DIKit's three authenticated ISA bindings still need
an explicit initialization step on iPad. A Mach-O symbol resolver
does not substitute the factory's returned pointer for a non-lazy data import.

## Isolated two-phase DIKit loader

`diskimagekit-static-bootstrap-build-v12` supplies a private loader, probe and
derived genuine DIKit image. It replaces only the optimized-cache StaticArray
CN import with an invalid private sentinel, not another Swift class. The loader
creates the completed subclass metadata first, loads the audited DIKit image,
then signs the three ISA slots with their original DA/address-diverse `0x6ae1`
contract. It publishes a DIKit handle only after actual PAC authentication and
restoration of the page's original current and maximum protections.

The original cache, ObjC loader source and image audit establish no eager
Mach-O initializer, non-lazy class, category/load or Swift replacement/access
function path that consumes these objects during loading. The two genuine
Swift classes do have lazy metadata initializers; they remain outside this
pre-bootstrap execution. The diagnostic requires a fresh, single-threaded
process without `OBJC_`/`DYLD_` settings. Any failed transaction requires the
owning process to exit; a partially loaded image must not be reused through
global ObjC/Swift class discovery. These are explicit new private loading
semantics, not a restoration of the original CN export or full original closure.

Native Mac tests passed 245 bootstrap checks, including all 168 required imports,
20 real protocol-requirement PAC authentications, and all three ISA slots before
and after binding. Nine genuine metadata accessors passed 33 checks. A compiler
produced Swift fixture, with runtime UUID and canonical path checks before its
first call, passed 4,608 checks over 1,024 original DIKit getter/witness calls.
It exercises `BlockSize.allCases`, the `CaseIterable` witness, copy-on-write,
append, modification and removal. Injected failures after writes 1, 2 and 3
restored all three authenticated sentinels, exact current/max protections, and
published no handle. The third static array's private C-string entry has an
unproven aggregate call ABI and is not invoked by this fixture.

This functional test exposed a separate real PAC failure in the previous
relative-data image: protocol requirement GOT pointers had incorrectly been
treated as plain data. The original per-slot cache words and compiler IR prove
DA/address diversity/`0x7d4c`. Restoring those 20 contracts fixes the genuine
`CaseIterable` witness crash; class `MethodDescriptor` authentication `0x675a`
is a different ABI. Frozen failed candidates are preserved as controls.

The iOS candidate is strictly compiled and signed with the four probe rights,
but has not run on iPad. Its strong DiskImages2 dependency still requires the
separate modern provider. Native Mac array success and prior iPad metadata-only
success do not establish that this integrated loader is functional on iPad.

## Remaining boundaries

DIKit 27 additionally requires its own strong dependency closure, repaired
relative metadata, and a compatible modern DiskImages2 implementation. The iPad
DiskImages2 method inventory found incompatible old classes and aggregate ABIs;
the old framework is not accepted as a modern DIKit provider. The separate POSIX
disk queue's 4,295 checks do not verify Apple's `io_rings`/`libuio` ABI or its
integration into the original VirtualMachine 27 block device.

These candidates are isolated diagnostics. They do not change iPadOS, production
runtime files, or the published release. Device probes use only the four scoped
rights in their manifests: platform application, private no-container, private
no-sandbox, and private can-execute-cdhash. Providers themselves have no rights.
